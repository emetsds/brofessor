### 1. Логическая структура каталогов кода — выполнено 07.11.2026

Сохранить существующий `src`-layout и одно устанавливаемое приложение. Внутри `brofessor` сгруппировать интерфейсы, общие сервисы, предметные возможности и инфраструктуру. Это выбор по текущим ответственностям проекта; единого обязательного дерева каталогов для Python-приложений нет. Назначение `src`-layout и проверка установленного пакета описаны в [PyPA](https://packaging.python.org/en/latest/discussions/src-layout-vs-flat-layout/) и [pytest](https://docs.pytest.org/en/stable/explanation/goodpractices.html).

Целевая структура:

```text
src/brofessor/
  __init__.py
  models.py                     # общие Pydantic-контракты
  interfaces/
    cli/                        # точка входа Typer и группы команд
    web/
      app.py                    # запуск Streamlit и сборка экранов
      pages/                    # задачи, источники, заметки, проекты, поиск
      dialogs/                  # настройки и диалоги действий
      components/               # редактор, навигация, прогресс, recovery, стили
      assets/                   # используемые UI-компонентами JS-файлы
  application/                  # общие сервисы, pipeline, worker, задачи, проекты
  features/
    sources/                    # коллекции, чтение, навигация по оригиналам
    questions.py
    reports.py
    studies.py
    podcasts/                   # сценарии, серии, автор по оригиналам, сверка
    books/                      # перевод, терминология, аудиокниги
  infrastructure/
    storage/                    # SQLite workspace, preferences, OS-locks
    text/                       # bounded runners Codex/Claude/Ollama, guardian
    agents/                     # существующий адаптер навигации Pydantic AI
    speech/                     # TTS, каталог моделей, референсы, подготовка речи
    formats/                    # импорт/экспорт EPUB/PDF, PPTX, монтаж аудио, шрифты
  prompts/                      # человекочитаемые шаблоны и их загрузка, этап 2

tests/
  application/
  features/
  infrastructure/
  interfaces/
  prompts/
  helpers/                      # общие синтетические модели и построители fixtures
  fixtures/                     # исходные проверочные материалы и provenance

tools/                          # явные локальные пробы и проверки разработчика
docs/                           # требования, архитектура, единый план и отчёты
```

Каталоги создавать по мере переноса реальных модулей. Контракты конкретного формата держать рядом с его реализацией; `models.py` оставлять для действительно общих типов. ### 3. Именованные значения и строковые контракты во всей кодовой базе — выполнено 07.11.2026

Цель: у повторяемого значения с единым смыслом есть понятное имя, владелец и доступные для навигации использования. Статусы, виды операций и другие закрытые наборы описаны явно; структуры общих записей известны вызывающему коду. Объём включает `src/brofessor`, `tests`, `tools`, Python/JS-границы UI и связанные ресурсы JSON/Markdown. Исходные материалы, сторонний код и содержимое пользовательских проектов в рефакторинг не входят.

**Основание плана:** первичный AST-обзор охватил 183 Python-файла, из них 103 в приложении. Например, литерал `podcast` встречается в 15 модулях приложения, `succeeded` — в 19, `queued` — в 17; это кандидаты для разбора по смыслу, а не метрика качества или норматив количества строк. Ключи словарей `id`, `kind`, `params`, `status`, `revision` тоже массово повторяются; для общих записей нужно описать структуру, а не механически вводить константу для каждого ключа. Исходный полный набор: **753 passed / 58,31 с**. Перед правками сохранены рабочий срез и схемы 59 Pydantic-моделей во временном каталоге; принятые исходные схемы закреплены синтетическими SHA-256 в `tests/fixtures/contracts/`.

#### Правила выбора представления

- Закрытый набор предметных значений — `StrEnum` с явно заданными прежними строками: `JobStatus.RUNNING = "running"`. `auto()` для сохраняемых значений не использовать: переименование Python-символа не должно менять SQLite, JSON или ключ кеша. Разные понятия получают разные типы, даже если часть значений совпадает: статус job, состояние этапа, продолжение первой озвучки и отображаемый статус задачи имеют разные допустимые наборы.
- Отдельное повторяемое значение с единым назначением — константа уровня модуля в `UPPER_CASE`; внутреннее имя начинается с `_`. Для публичных контрактных констант использовать `Final`. Связанные правила отбора — именованные неизменяемые группы, например `ACTIVE_JOB_STATUSES`, `RESUMABLE_JOB_STATUSES`, `TEXT_JOB_KINDS`. Состав группы определяется её поведением: одинаковое текущее содержимое само по себе не повод объединять разные правила.
- Общие записи задания, редакции, прогресса, источника и подключения — именованные типы вместо голого `dict` на межмодульных границах. Начать с `TypedDict`, сохраняя нынешнюю форму данных и словарный доступ; существующие Pydantic-модели оставить границей runtime-валидации. `dataclass` нужен только для внутреннего объекта с собственной ответственностью. `TypedDict` и `Final` сами не обеспечивают runtime-проверку.
- Повторяемые `Literal` описывать именованными типами, сохраняя точные допустимые подмножества. Например, статус доказательности с двумя вариантами не расширять до трёх только ради общего enum. Pydantic-поля переходят на enum либо на `Literal` из его членов в зависимости от сохранения внешней схемы.
- Действительно общие определения разместить в небольшом пакете `contracts/`: `jobs.py` — виды заданий, состояния и общие записи; `text.py` — провайдер и текстовое подключение; `content.py` — общие языки, роли и доказательность. Эти модули не импортируют application services, хранилище, UI или SDK. `models.py` сохраняет общие Pydantic-результаты; предметные и форматные определения остаются рядом со своим владельцем. Общего файла со всеми константами и статических классов-контейнеров не добавлять.
- Локальные очевидные литералы (`"utf-8"`, режимы открытия, разделители), единичные сообщения, содержимое промптов, CSS/HTML и имена внешних полей оставлять там, где имя не добавляет смысла. Повторяемые сообщения объединять при общей семантике и едином владельце. Открытые данные — ID моделей, пути пользователя, source IDs, имена терминов — не превращать в закрытый enum. Каталоги моделей и промптов сохраняют роль источника данных.

Основания выбора: [PEP 8 о константах](https://peps.python.org/pep-0008/#constants), [StrEnum](https://docs.python.org/3.12/library/enum.html#enum.StrEnum), [Literal / TypedDict / Final](https://docs.python.org/3.12/library/typing.html), [Pydantic о JSON Schema](https://docs.pydantic.dev/latest/concepts/json_schema/). Это правила данного рефакторинга, а не утверждение, что Python требует именовать каждую повторяющуюся строку.

#### Совместимость, которую нужно сохранить

Сохраняемые строки, поля и значения JSON, публичные команды/опции CLI, допустимые параметры и выбор провайдера остаются прежними. Схема SQLite не требует новой версии; прежние jobs, пользовательские редакции, исходники, заметки, артефакты и snapshots открываются без переписывания. Сохранить ключи идемпотентности, checkpoints, сегментов речи и recovery, имена файлов/locks, ID и версии промптов. Браузерные ключи и порядок событий редактора не меняются из-за переименования Python-символов. Обработка старых данных и неизвестных значений сохраняет нынешние правила; enum не должен незаметно заменять их дефолтом или запрещать раньше поддержанные записи.

**Проверенный риск:** `application/pipeline.py` включает `model_json_schema()` в идентичность inference. Локальная проба с установленным Pydantic **2.14.2** показала: замена `Literal["ru", "en"]` на enum-поле меняет схему; `Literal[Language.RU, Language.EN]` при тех же имени модели и полях сохранил её. JSON и SQLite в этой пробе сохранили прежнюю строку. Это проверка выбранного приёма на одном поле, а не доказательство совместимости всех моделей. Для каждой изменяемой выходной модели сравнивать прежнюю схему, defaults и сериализованный результат; сохранять прежние схемы и хеши без добавления версии ради стиля. Неизменность только множества допустимых значений недостаточна: порядок, `$defs`, заголовки и defaults тоже могут менять хеш.

## Общие правила развития

- Показывать и принимать только параметры выбранного действия. Наследовать подходящие предпочтения, явно обозначать переопределения. Редкие опции раскрывать в контексте, сохраняя привычный минималистичный UI.
- Использовать общие сервисы, очередь, checkpoints, отмену/продолжение и равноправные CLI/UI. Новая возможность не требует отдельного сервера, очереди или универсальной платформы заданий.
- Сохранять оригиналы, проверяемые локаторы, пользовательские правки, версии и замороженные входы операций. Переиспользовать подходящие законченные этапы при повторе.
- Сохранять выбранные текстовые подключения и явные границы передачи данных. Подписочный CLI не заменять платным API. Для новых локальных компонентов проверить лицензии кода, весов, шрифтов и иных поставляемых ресурсов; предпочтение — свободным лицензиям и закреплённым стабильным версиям.
- Обычный результат должен быть готов к использованию. Проба фрагмента, правка термина или реплики — необязательные способы исправить замеченную проблему. Контрольная вычитка и прослушивание при разработке не становятся обязательной работой каждого пользователя.
- Шаблоны письменных материалов использовать внутри общего пути подготовки отчёта. Отдельный тип задания добавлять, когда ему нужны особые входы, процесс или результат.

## Проверки при реализации

Использовать существующее окружение: `uv run --no-sync pytest -q`, `uv run --no-sync ruff check .`, `uv run --no-sync ruff format --check .`. Запускать проверки по изменённым границам; обычные тесты не требуют подписки, сети или весов. Настоящие вызовы, содержательную сверку и визуальную/слуховую оценку записывать отдельно в `docs/experiments/`.

В первом этапе P1 выполнены два настоящих текстовых вызова и 126 связанных offline-проверок. В следующем — четыре вызова на том же синтетическом материале и 167 целевых проверок core/worker/CLI/UI. Затем — 6 вызовов на целой книге и 2 адресных контроля новых правил, 199 целевых offline-проверок. Слуховая приёмка и новые генерации аудио не выполнялись. Полный прогон остальных продуктовых сценариев не повторялся.

05.11.2026 для PDF выполнены два настоящих вызова и локальная пересборка без модели, проверены фактическое содержимое и вид страницы, открыт настоящий UI. Полный offline-набор: **552 passed**; Ruff check/format, diff check и сборка wheel проходят. Реальная приёмка прежних аудио/PPTX/EPUB заново не выполнялась.

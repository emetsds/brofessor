# План реализации brofessor

Дата: 01.11.2026. Статус: план подготовлен, продукт не реализован. Это единственный список задач реализации. Требования: [requirements.md](requirements.md). Решения: [architecture.md](architecture.md). Основания: [research.md](research.md).

Текущая задача ограничена созданием локального репозитория и плана. Выполнение этапов ниже начинается по запросу на реализацию. Указанные пакеты и команды пока являются планом, а не инструкцией запуска готового продукта.

## Итог первой версии

В CLI и локальном Streamlit UI можно создать workspace, добавить несколько источников, задать вопросы с проверяемыми ссылками, подготовить подкаст/серию RU/EN и редактируемый PPTX. Целевой набор исполнителей: Codex, Claude Code и Ollama с проверенной открытой моделью. Общее состояние переживает перезапуск интерфейса и позволяет продолжать задания.

Первый полезный результат появляется уже в P0: короткое аудио и PPTX по одной главе, запускаемые из минимальных CLI и UI. Личный сценарий принимается на доступном Codex и локальных моделях. Отсутствие доступа к Claude не блокирует эти результаты и следующие этапы. Интеграция Claude при этом остаётся обязательным пунктом плана со своим фактическим статусом: полная поддержка всех трёх исполнителей объявляется только после настоящих проверок каждого.

## Порядок и зависимости

```text
P0: chapter -> short audio + PPTX through CLI/UI
          |
P1: contracts, workspace, worker, CLI/UI skeleton
          |
     +----+----+
     |         |
P2: sources  P3: executors
     |         |
     +----+----+
          |
P4: grounded Q&A + reusable chapter drafts
          |
     +----+----+
     |         |
P5: podcasts P6: slides
     |         |
     +----+----+
          |
P7: release acceptance, portability, packaging
          |
P8: wider sources and Google Slides
```

После P1 импортёры и исполнители можно разрабатывать параллельно. После P4 независимы audio и slides. Общие contracts меняются согласованно. Calendar estimates определяются после P0, количество этапов не является оценкой в днях.

## P0. Проверить дорогие предположения

Требования: R06–R09, R11–R12. Результат: измерения и решение о первом проверяемом наборе инструментов.

- [ ] Сделать fixture собственного авторства: главы с фактами в начале/середине/конце, числа, имена, английские термины, конфликтующие сведения и вопрос без ответа. Приватную книгу использовать только для отдельной локальной проверки.
- [ ] Проверить стабильный Codex CLI с существующей подписочной авторизацией: ограниченный текстовый task → валидный JSON. Не читать token files. Зафиксировать версию, auth mode, итог и лимиты, без секретов.
- [ ] Проверить тот же task через Claude Code, если доступен вход. Наличие бинарника не считать доступом к модели. При недоступности оставить настоящий smoke test незавершённым, не подменять его mock.
- [ ] Проверить Ollama local-only с одной подходящей открытой моделью: JSON schema, русский вопрос к английскому тексту, контекст, время и память. Зафиксировать модель, квантование, ревизию и лицензию.
- [ ] Сравнить Qwen3-TTS и Chatterbox на 60–90 сек текста, затем на 3–5 мин двухголосого диалога RU и EN. Измерить wall time, audio duration, peak memory и число дефектных реплик. Проверить происхождение voice references.
- [ ] Собрать 4–5 редактируемых слайдов и открыто воспроизводимое превью без зависимости от Codex bundled runtime. Проверить русский шрифт, таблицу, схему, notes и ссылки.
- [ ] Провести минимальный Streamlit spike: submit → отдельный worker → progress. Обновить/закрыть страницу и увидеть единственное продолжающееся задание после возвращения.
- [ ] Связать эксперименты в один путь: одна глава → доступный исполнитель → короткий двухголосый подкаст и редактируемый PPTX. Запустить через минимальные CLI и Streamlit, вызывающие общую функцию. Сравнить два пользовательских фокуса. Получить реальные файлы, а не только сценарий и план слайдов. Для этого достаточно одного формата входа и одного исполнителя.
- [ ] Записать результаты в будущий `docs/experiments/feasibility.md` и выбрать по одному базовому text/TTS профилю. Прототипы этого этапа не объявлять готовым core.

Выход: подтверждена возможность получить нужные данные и артефакты с доступными ресурсами. Если локальная озвучка не проходит порог, сначала проверить второй кандидат и ограниченную альтернативу. Облачная озвучка допустима только после проверки включённых Pro-кредитов и явного профиля без новых расходов. Не маскировать блокер дополнительной инфраструктурой.

## P1. Общее ядро и жизненный цикл задания

Требования: R01, R08, R10–R12. Предлагаемые области: `src/brofessor/domain`, `application`, `storage`, `jobs`, `cli`, `ui`, `tests`.

- [ ] Создать Python package/uv lock, extras, линтер и тестовый запуск. Описать единый `ApplicationServices` и схемы ошибок.
- [ ] Ввести Source/Revision/Locator, EvidenceBundle, TaskRequest/Result, Draft, Artifact, Job/Stage и версию workspace schema.
- [ ] Реализовать workspace с SQLite и файлами, миграции, относительные пути, backup/export/import и защиту авторских revisions.
- [ ] Реализовать очередь одного worker, атомарный claim, heartbeat/lease, checkpoints, дедупликацию submit, восстановление и отмену subprocess tree.
- [ ] Добавить ProcessManager без автозапуска при входе в ОС. Worker независимо переживает закрытие CLI и UI.
- [ ] Создать тонкие Typer и Streamlit клиенты: пространства, задания, события и диагностика. Начать с детерминированного fake executor.
- [ ] Проверить двунаправленный сценарий: CLI создаёт → UI отменяет/возобновляет и наоборот. Проверить два одновременных submit, два worker, аварийное завершение и перезапуск.

Выход: интерфейсы разделяют реальное состояние. Refresh не запускает работу заново. Offline unit/integration tests выполняются без модели, сети и подписки.

## P2. Импорт и проверяемый корпус

Требования: R01–R03, R12. Области: `ingest`, `sources`, `retrieval`, fixtures.

- [ ] Добавить PDF с текстовым слоем, EPUB по spine, Markdown/TXT. Сохранить originals, hash, importer version и отображение локаторов.
- [ ] Обнаруживать дубликаты, обновлённые версии, пустое извлечение, повреждённые файлы и сканы. Отчёт об ошибках доступен в обоих интерфейсах.
- [ ] Реализовать карту разделов, coverage ledger и отдельный редакционный отбор. Не сводить чтение книги к поиску top-k.
- [ ] Добавить локальный поиск и получение оригинального фрагмента по ссылке. Протестировать multi-source и одинаковые названия файлов.
- [ ] Подключить upload/path import, список, просмотр и coverage в UI/CLI. Проверить traversal в именах и разумные ограничения загрузки/распаковки EPUB.

Выход: все единицы контрольного корпуса учтены, факты из начала/середины/конца находятся, цитата воспроизводимо открывается. Перезапуск не требует повторного импорта.

## P3. Независимые исполнители и переносимый skill

Требования: R09, R11–R12. Области: `executors`, `skills/brofessor`, installer, contract tests.

- [ ] Реализовать capability/status для выбранного исполнителя, контекстные бюджеты, timeout, cancellation и ограниченные retries. Неподдерживаемое выявляется до запуска длинной работы.
- [ ] Реализовать CodexRunner на официальном стабильном CLI, структурированный вывод, ограниченную область доступа и нормализацию ошибок авторизации/квот.
- [ ] Реализовать ClaudeCodeRunner на официальном `claude -p`, с ограниченными tools и без `--bare` при подписочном входе. Явно выявлять API-billing профиль, не молча наследовать его как разрешение расходов.
- [ ] Реализовать OllamaExecutor на native API, local-only профиль и проверку конкретной модели. Уменьшать размер задач под доступный контекст, а не молча обрезать источник.
- [ ] Поддержать cooperative `task prepare/accept` для текущего агента и единый canonical Agent Skill. Добавить установку в поддерживаемые каталоги Codex и Claude без дублирования workflow.
- [ ] Добавить выбор профиля и диагностику в CLI/UI. Сохранять provenance исполнителя в каждом результате.
- [ ] Прогнать одинаковые contract fixtures через все адаптеры, а затем настоящие smoke tests для каждого доступного доступа. Проверить malformed output, missing citation, rate limit, timeout и отмену.

Выход: задача одного типа переносится между исполнителями без изменения domain schema. Отдельно отмечены проверки поведения и фактического доступа. Ни один runner не получает расширенные permissions из текста источника.

## P4. Вопросы, заметки и пилот одной главы

Требования: R03–R05, R08–R09.

- [ ] Реализовать source selection, retrieval, evidence bundles и ответы с утверждениями/ссылками. Разделять данные источника и собственную интерпретацию.
- [ ] Добавить многошаговые уточнения, сохранённые вопросы/ответы и заметки без зависимости от истории конкретного агента.
- [ ] Прогнать контрольные вопросы: несколько источников, конфликт, недостаток данных, русский запрос к английскому материалу. Измерить retrieval recall и обоснованность утверждений.
- [ ] При недостаточном поиске добавить локальные embeddings с измерением эффекта, сохранив baseline и возможность перестроить индекс.
- [ ] Реализовать brief, аудиторию, фокус, план, проверку источников и версии ручных правок. Смена фокуса сохраняет исходное извлечение.
- [ ] Сделать по одной содержательной главе сценарий на 5–7 минут и план 4–5 слайдов. Проверить смысл и различие результатов для двух фокусов.
- [ ] Подключить одинаковые возможности в чат/формы Streamlit и CLI. Ссылки открывают исходный fragment, а не только сгенерированный конспект.

Выход: есть полезное исследовательское пространство до длинной озвучки. Успешная schema validation не подменяет оценку содержания.

## P5. Подкасты, языки и серии

Требования: R05–R06, R08, R10.

- [ ] Реализовать PodcastPlan: темы, длительность, роли, языки, словарь терминов и ссылки. Отдельный общий план для серии предотвращает повторы и провалы между выпусками.
- [ ] Реализовать выбранный SpeechBackend, стабильные voice profiles, сегментацию, WAV checkpoints и независимую перегенерацию одной реплики.
- [ ] Добавить монтаж, нормализацию, паузы, MP3, измерение длительности и главы/таймкоды в сопроводительном файле.
- [ ] Добавить аудиоплеер/скачивание в UI и те же артефакты/управление в CLI. Показать фактическую длительность и ошибки.
- [ ] Проверить выпуск 20–30 минут целой книги, затем 60 минут и серию. RU и EN проверяются отдельно. Контроль полноты через ASR может помогать, но не заменяет слуховую проверку качества.
- [ ] Проверить crash/resume, отмену и изменение одной реплики/голоса: неизменённые этапы не выполняются повторно, устаревшие результаты не переиспользуются.

Выход: измеренное аудио соответствует требованиям, рабочая скорость и память опубликованы с условиями замера. Голоса и условия лицензии подтверждены для выбранного профиля.

## P6. Редактируемые презентации

Требования: R05, R07–R08, R10.

- [ ] Реализовать SlidePlan с независимым фокусом, ссылками, notes и несколькими простыми типами слайдов.
- [ ] Собрать Node/PptxGenJS renderer с зафиксированными зависимостями, одним качественным шаблоном, редактируемыми текстом/таблицами/простыми схемами.
- [ ] Генерировать превью через выбранный в P0 переносимый renderer. Проверять переполнение, шрифты, ссылки, читаемость и редактируемость.
- [ ] Подключить создание, редактуру содержимого, превью и получение PPTX в обоих интерфейсах. Пересборка слайдов не запускает TTS.
- [ ] Проверить презентацию по главе и по целому корпусу. Растровые иллюстрации допустимы, подмена всего слайда изображением - нет.

Выход: готовый файл можно открыть и отредактировать, а его содержание прослеживается к источникам. Google Slides не объявляется проверенным по одному факту существования PPTX.

- [ ] Проверить локальный режим без внешних запросов после установки весов/зависимостей. Проверить отсутствие автоматического cloud/API fallback.

- [ ] Добавить offline CI, отдельные opt-in integration tests и инструкции для тестов реальных моделей. Не запускать подписочные аккаунты на публичных CI runners.

Выход: измеренно выполнен весь пользовательский цикл, CLI/UI равноправны, статусы интеграций честные. Критерий завершения - рабочие сценарии и артефакты, а не количество модулей.

## Проверки и отчётность

При реализации базовые offline checks планируются как `uv run pytest`, `uv run ruff check .` и согласованная проверка типов. Streamlit AppTest проверяет формы и состояние интерфейса, отдельный browser smoke test - реальный пользовательский путь. Тесты runners проверяют протокол с fake subprocess/HTTP и отдельно настоящий provider.

Для каждого этапа в этом файле отмечается только фактически выполненное. Результаты тяжёлых экспериментов, версии и артефакты фиксируются в `docs/experiments/` при появлении. В текущем planning-only репозитории runtime tests ещё отсутствуют и не заявляются пройденными.
